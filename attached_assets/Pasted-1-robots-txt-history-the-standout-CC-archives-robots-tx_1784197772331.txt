1. robots.txt history — the standout
CC archives robots.txt per crawl, in its own bucket. You saw it in your dump:
"filename": ".../robotstxt/CC-MAIN-20260610112837-...warc.gz"
That means you can fetch any domain's robots.txt as it stood in every crawl since 2013, and diff it.
So you can date, precisely and at scale: when did each publisher block GPTBot? CCBot? ClaudeBot? Not approximately — to the crawl.
Now join that against your 22.7M citations. blocked_date vs citation_trend. That's the study. Did blocking GPTBot actually cost anyone visibility, or did retrieval route around it? Nobody has an answer because nobody's built the timeline. You can build it from free data.
This is the best idea in this message. It might be better than the homepage post.
2. Response headers from the WARC
WARC stores the full HTTP response — headers included. Byte-range fetch gets you them. That surfaces things HTML inspection can't:

X-Robots-Tag: noindex — noindex served as a header. Invisible in view-source. Sites ship this by accident constantly, usually a staging config that escaped.
Link: rel="canonical" — canonical via header, not tag. Overlooked by every crawler tool.
Cache-Control, Vary, CDN identification, server stack.

A page 200-ing in CC with a header noindex is doing nothing for you anywhere. Free to check, nobody checks it.

5. lastmod lie detector
Sitemap says lastmod: 2026-07-01. CC digest hasn't changed across six crawls.
The sitemap is lying. Usually a CMS stamping lastmod on every build regardless of whether content changed. Google is widely believed to discount lastmod precisely because so many sitemaps do this — you can now prove whether a given site is one of them.
Great audit finding, and a great benchmark study.
6. Corpus inception date
Walk backwards through crawls. Find the first one containing a domain or URL.
That's when the open web first saw you — observed, not claimed. Google's historical-data patent family treats document inception date as a ranking input. You can't see Google's copy. You can compute CC's.
Per-page version is useful too: first_crawl - publish_date = discovery lag, benchmarked against competitors. "Your posts get crawled 40 days after publish. Theirs, 8."

Count path segments per URL. Plot presence rate by depth.

Classic crawl-budget logic, but nobody's ever shown a client the actual wall on their own site. Visually devastating in a report.

10. The languages field
CC runs language detection per document and it's multi-valued ("eng,fra").
For international sites: does CC see all your locales? Is your Spanish page detected as spa — or eng, because the nav is English and the body is thin? Cross-check against hreflang.
Nobody is auditing hreflang against an actual language-detection ground truth. This is a free one.
11. mime vs mime-detected
Server declares one thing, CC detects another. Real bug class — misconfigured content-type. Two fields, one comparison.
12. Crawl trap detection
Per-parameter value cardinality:
?date= → 400 distinct values     ← calendar trap
?color= → 8 distinct values      ← normal facet
High cardinality on one param = infinite space. Ecommerce and event sites are riddled with these.
13. Wayback join — free coverage doubling
The Internet Archive CDX API uses the same protocol (both run pywb). Same query shape:
http://web.archive.org/cdx/search/cdx?url=example.com&matchType=domain&output=json
Wayback goes back to 1996 and crawls far more often. Join the two and your history gets dense enough for real trend work — and it costs you nothing but a second fetch. Different crawler, different biases, so disagreements between them are themselves informative.
